# Architecture

This describes the system as built. The visual reference audit is in `REFERENCE_AUDIT.md`; the build history and status are in `IMPLEMENTATION_PLAN.md`.

## 1. Stack

| Layer | Choice | Notes |
|---|---|---|
| Framework | Next.js 15.5 (App Router), React 19.1, TypeScript strict | Server components for content, client components only where motion or interaction needs them |
| Styling | Tailwind CSS v4 + `src/styles/tokens.css` | Public pages use hand-written CSS (`src/app/(site)/site.css`) built on the tokens; the admin uses Tailwind utilities |
| Motion | GSAP 3.15 + ScrollTrigger, `@gsap/react`, Lenis | Public site only. Framer Motion is installed for admin micro-interactions only, so it never ships to public pages |
| Data | PostgreSQL 14+ and Prisma 6.19 | Prisma runs on the **JS query compiler + `@prisma/adapter-pg`**: no native query-engine binary is downloaded or needed at runtime |
| Migrations | SQL files generated by `prisma migrate diff`, applied by `scripts/migrate.ts` | Prisma-compatible `_prisma_migrations` table with checksums and an advisory lock (see §8) |
| Validation | Zod 4 (shared client/server) | Section schemas, admin forms, contact brief |
| Forms | React Hook Form + `@hookform/resolvers` | Contact brief wizard and admin forms |
| Auth | Custom session auth: scrypt password hashes (`node:crypto`), opaque session token, sessions table | No third-party auth dependency |
| Media | `local` driver (disk + on-the-fly resizing with `sharp`) or `cloudinary` driver, chosen by `MEDIA_DRIVER` | Both sit behind one `StorageDriver` interface |
| Rich text | Tiptap 3 in the admin → ProseMirror JSON in the DB → rendered server-side by `RichText.tsx` | No raw HTML is ever stored or rendered |
| Drag and drop | dnd-kit | Sections, menus (keyboard accessible) |
| Email | Nodemailer over `SMTP_URL`; without it, notifications go to the server log | Contact brief notifications |
| Tests | Vitest + Testing Library, Playwright (functional e2e, geometry comparison, pixel baselines) | See `TESTING.md` |

The site is **English only**. There is no locale segment in URLs and no translation tables.

**Draft vs published.** `PageSection` rows are the working copy. Publishing snapshots the enabled sections into the owner's `publishedSections` JSON and sets `status = PUBLISHED`. Public pages render only that snapshot, so editing never changes the live site until someone publishes. Draft preview renders the working copy.

## 4. Section system

`src/sections/fields.ts` exports small field builders (`f.text`, `f.richtext`, `f.media`, `f.link`, `f.select`, `f.boolean`, `f.number`, `f.refs`, `f.strings`, `f.list`). Each builder produces three things at once: a Zod schema, a default value and a UI descriptor.

`src/sections/registry.ts` defines the 32 section types from those builders: heroFilm, pageHero, pageIntro, statement, studioIntro, disciplineScene, disciplinesStrip, disciplineRows, figures, caseReel, clientWall, featurePanel, gateway, newsStrip, briefCta, chapter, servicesList, editorial, keepExploring, caseInsights, caseChapter, caseMedia, imageRow, vision, method, workWall, caseIndex, articleList, contactIntro, contactBrief, richText, legal.

- The **admin form** (`SectionFieldsForm`) is generated from the descriptors, so adding a field to a section means editing one line in the registry.
- **`SectionRenderer`** validates every section with `safeParse`. An invalid or unknown section is skipped (and logged); in draft preview an inline notice explains why.
- Media references and entity references are collected from section data (`collectMediaIds`, `collectRefs`) so each page loads its media in one query, and the media library can show where a file is used.

## 5. Rendering, caching, preview

- Public routes are server components with ISR (`revalidate = 3600`). Dynamic segments return `[]` from `generateStaticParams`, so pages render on first request and are then cached.
- Every admin mutation calls `revalidatePath("/", "layout")`, so a publish shows up on the next request.
- Admin mutations are server actions wrapped in `guarded()`: authorise (`requirePermission`), validate (Zod), write, store a `ContentRevision` and an `AuditLog` row, revalidate. Errors come back as typed results that the admin shows as toasts.
- **Draft preview** uses Next.js Draft Mode. `/api/preview?token=…` requires both a valid HMAC token (15-minute TTL, signed with `SESSION_SECRET`) and a signed-in admin session. Preview responses carry `X-Robots-Tag: noindex` and show a preview bar with an exit link.
- **Redirects**: `middleware.ts` (Node.js runtime) reads enabled rows from `Redirect` through a small `pg` pool, caches them for 30 seconds per instance, and answers with 308 (permanent) or 307.

## 6. Motion

- `MotionProvider` (client, in the site layout) creates Lenis, drives it from `gsap.ticker`, and runs declarative effects from data attributes: `data-split` (word rise), `data-reveal`, `data-parallax`, `data-scrub-words`, `data-count`.
- Rich scenes run only when `(min-width: 901px) and (orientation: landscape) and (hover: hover) and (pointer: fine) and (prefers-reduced-motion: no-preference)` matches, the same gate the reference uses. Otherwise every section renders as normal stacked flow.
- A boot script adds `js-motion` to `<html>` before paint so elements can start hidden without a flash; a 4-second failsafe removes the hidden state if scripts fail. Without JavaScript all content is visible.
- Pinned scenes (hero film, cinema hero, discipline cross-fade, case reel, vision, method) use `useGSAP` with `gsap.matchMedia`, so they clean up on route change and on breakpoint change.
- Page transitions: a curtain wipe intercepts internal link clicks in the capture phase, navigates under the curtain and scrolls to the top.
- Only `transform`, `opacity` and `clip-path` are animated.

## 7. Security

- RBAC is enforced on the server in every server action and admin route handler. Every export of a `"use server"` file is reachable from the browser, so read helpers are guarded too.
- Passwords: scrypt (N = 2^15) with per-password salt; constant-time comparison. Login is throttled per email and per IP through `LoginAttempt`.
- Sessions: 32-byte random token in an `httpOnly`, `SameSite=Lax`, `Secure` (production) cookie; only its SHA-256 hash is stored. Signing out deletes the row; users can revoke their other sessions from Profile.
- Uploads: size limit, MIME allow-list, and magic-byte sniffing (the declared type must match the file's signature). The admin upload route also checks the `Origin` header.
- Contact brief: Zod validation, honeypot field, 5 submissions per 10 minutes per IP.
- CSV export neutralises spreadsheet formulas (`=`, `+`, `-`, `@` prefixes).
- Headers (`next.config.ts`): Content-Security-Policy, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` (DENY on admin), `Permissions-Policy`, `Cross-Origin-Opener-Policy`, HSTS in production. Admin responses are `noindex` and `no-store`.
- Secrets come only from the environment; `.env.example` documents every variable.

## 8. Migrations without native engines

The Prisma schema engine binaries could not be downloaded in the build environment, and the WASM schema engine could not introspect PostgreSQL 16. So:

1. `npm run db:migration:new -- <name>` runs `prisma migrate diff` from `prisma/migrations/schema.snapshot.prisma` (the last applied schema) to `prisma/schema.prisma`, writes the SQL to a new migration folder, and updates the snapshot.
2. `npm run db:migrate` (`scripts/migrate.ts`) applies pending folders in order inside transactions, under a PostgreSQL advisory lock, recording each one in `_prisma_migrations` with a SHA-256 checksum. `--status` lists applied and pending migrations. A changed checksum stops the run. When `DATABASE_URL` points at a transaction pooler, set `DIRECT_DATABASE_URL` for the runner, because advisory locks need a direct session.

The table format is the same one Prisma uses, so switching back to `prisma migrate deploy` later works without changes.

## 9. SEO

- `buildMetadata` (`src/lib/seo/metadata.ts`) builds title, description, canonical, robots, Open Graph and Twitter tags from the entity's `SEOSettings`, falling back to the entity's own fields and then to the global defaults.
- JSON-LD: `Organization` and `WebSite` on every page; `BreadcrumbList` on inner pages; `Service`, `CreativeWork` and `Article` on their detail pages.
- `sitemap.ts` lists published pages, services, case studies and articles that are indexable and not excluded from the sitemap. `robots.ts` disallows `/admin` and `/api/`, and blocks everything when `ALLOW_INDEXING=false` or on Vercel preview deployments.
- The admin SEO dashboard lints every published entity (length bounds, missing description or image alt text, duplicate titles, noindex pages still in the sitemap, focus keyword missing from the title) and manages redirects.
